Gratitude

Peer-to-peer mutual aid coordination, built on Gemma 4.

Two neighbors. One has something to offer — food, a ride, an hour of company. One needs something. Right now, matching them takes days of phone trees, Facebook posts, and clipboards at the church — and the people who get help are mostly the people who already know who to call. Gratitude does that matching in seconds, on the phones people already have, for anything one neighbor can offer and anything another can need.

The motivating scenario is disaster response (e.g. the September 4 2025 Mesa County flooding), but the system is built for everyday mutual aid — disasters are the sharp edge of a continuous problem.

Try it on Android

Download APK (290 MB) Source on GitHub
  1. On your Android phone, enable Install unknown apps for your browser (Settings → Apps → your browser → Install unknown apps).
  2. Download the APK using the button above and open it. Android will prompt you to install.
  3. Launch Gratitude. The first run downloads the on-device Gemma 4 E-series weights (one-time, ~1.5 GB) over Wi-Fi.
  4. Tap a community skill (community-need, community-offer) and describe a need or offer in plain language. Watch Gemma classify it on-device into a structured, signed record.

This is an unsigned APK distributed for hackathon judging. It is signed with the Android debug key, not a Play Store key — Android will warn you accordingly. If you would rather not install an unsigned binary, the full source is on GitHub and the app builds with one Gradle command; see Build from source.

What you can do with the app alone: compose a need or offer in natural language, watch the on-device Gemma 4 model classify it into a UNSPSC code + structured fields, see the wire-format record before it is signed and transmitted. The demo backend has standing test offers and needs you can match against — post a matching need or offer and you should see a match notification within seconds.

What you can do with two devices: the full lifecycle — match notification, opt-in contact-share, end-to-end encrypted handoff of phone numbers between matched parties.

Build from source

For developers who want to verify that the binary matches the source, or who would rather not install an unsigned APK:

git clone https://github.com/colin-roy-ehri/gratitude
cd gratitude/Android/src
./gradlew :app:installDebug   # builds and installs to the connected device

A HuggingFace OAuth app is required for the model-download flow inherited from upstream Gallery — see DEVELOPMENT.md. To build a release APK matching the one above: ./gradlew :app:assembleRelease.

How it works

Gratitude is a two-tier system. Both tiers run Gemma 4.

On-device (Gemma 4 E-series, via LiteRT). The user describes a need or offer in plain language. A Gemma 4 E2B model running on-device classifies that utterance into one or more structured records — a UNSPSC category, a quantity, a time window, an approximate location. EmbeddingGemma-300m encodes the normalized query and matches it against a pre-computed index of every UNSPSC code in the extended taxonomy. The user's actual words never leave their phone.

Self-hosted backend (Fastify on Compute Engine, Gemma 4 via Vertex AI MaaS). The backend receives signed structured messages, runs deterministic geographic + categorical matching, and brokers libsodium-sealed contact-share blobs between matched parties. The matching itself is deterministic — Gemma 4 26B is only invoked for the optional community-pulse welfare summary.

The full architecture, message format, privacy boundaries, and Gemma 4 evaluation numbers are in the repo README.

Privacy, briefly

The server is structurally incapable of reading message contents or learning identities. What that means precisely:

  • Cannot see: user names, phone numbers, free-form message text, contact info shared between matched parties, or any stable identity-to-message linkage.
  • Can see: approximate location (lat/long to 2 decimal places), message timing, UNSPSC categories, public-key reuse within a session, the implicit social graph of who-matches-with-whom.

This precision matters more than a blanket "private" claim — the Firestore schema is in backend/README.md and makes the boundary auditable.
